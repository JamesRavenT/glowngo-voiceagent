## What was broken, and what fixed it

The workflow was deployed but **non-functional**. Three separate faults:

| Fault | Cause | Fix |
|---|---|---|
| Nothing responded at all | Workflow was `active: false`, `triggerCount: 0`. Production webhook URLs 404. Only the one-shot test URLs worked. | Published the workflow. |
| `create_booking` wrote blank rows | `Append Booking` had `mappingMode: "defineBelow"` with an empty `value: {}` — a full column schema but zero field mappings. | Restored `mappingMode: "autoMapInputData"`. |
| `reschedule_booking` could not find the row | `Update Booking` had `matchingColumns: []` and a literal `value: {"row_number": 0}`. | Restored `autoMapInputData` and `matchingColumns: ["reference"]`. |

**The repo artifact was correct. The live instance had drifted.**

This matters more than the individual bugs. `artifacts/n8n/booking.workflow.json` specified
`autoMapInputData` and `matchingColumns: ["reference"]` all along. The live workflow was
hand-edited in the n8n UI, and **the UI silently flips `mappingMode` from `autoMapInputData` to
`defineBelow` when you open and click around the column-mapping panel.** You do not get a warning.
The workflow keeps returning HTTP 200 while writing empty rows.

If you edit nodes in the n8n UI, re-verify the mapping mode before you trust it.

## An empty sheet used to break everything

Emptying the bookings sheet made `check_availability` return **HTTP 500**.

In n8n, **a node that emits zero items halts the chain.** With no rows in the sheet, the
`Read Bookings` node output nothing, the downstream Code node never ran, and `responseMode:
lastNode` had no result to return. The execution log still reported `success` — the workflow
did not error, it simply stopped early — which makes this fault easy to misread as an auth or
network problem.

A salon with no bookings should report every slot as free, not fail. Fixed by setting
**Always Output Data** on all four `Read Bookings` nodes, so an empty read emits one empty item
and the Code node still runs. Verified: 38 slots returned against an empty sheet.

This is now recorded in `artifacts/n8n/booking.workflow.json` as `alwaysOutputData: true` on
those four nodes.

### 2. Webhook auth — done

Kept below for reference. See "Webhook auth — closed" above for the verified result.

**In n8n** (must be done in the UI — the MCP integration cannot create credentials):

1. **Credentials → Add credential → Header Auth.**
2. Name it `Glow & Go webhook secret`. Header name: `X-Webhook-Secret`.
   Value: a long random string — generate with `openssl rand -hex 32`.
3. Open each of the four Webhook nodes → **Authentication → Header Auth** → select that
   credential. All four: `Check Availability`, `Create Booking`, `Reschedule Booking`,
   `Cancel Booking`.
4. Save and **re-publish** the workflow. Changes to a published workflow do not take effect
   until republished.

**In ElevenLabs**, for each of the four webhook tools, add a second request header alongside
`Content-Type`:

```json
{ "type": "value", "name": "X-Webhook-Secret", "value": "<the same random string>" }
```

Prefer ElevenLabs' **secret/auth connection** feature over a plaintext `value` header if you
intend to leave this running publicly.

**Then re-run the lifecycle test.** An unauthenticated call must now return `403`, and the
agent must still succeed. If you only check one, check that the agent still works — it is easy
to lock out your own agent here.

> Do not commit the secret. `artifacts/elevenlabs/*.json` is tracked; keep a placeholder there,
> exactly as `<N8N_HOST>` is handled.

## Deployment — push to `main` now deploys

Cloudflare Workers Builds is connected to `JamesRavenT/glowngo-voiceagent`, branch `main`:

```
Build command:   pnpm exec opennextjs-cloudflare build
Deploy command:  pnpm exec opennextjs-cloudflare deploy
```

`pnpm run build` alone would **not** work as the build command — it produces `.next` but never
`.open-next/worker.js`, which is what `wrangler.jsonc` points `main` at.

All `NEXT_PUBLIC_*` values live in Cloudflare **build variables**, not runtime `vars`. They are
inlined at build time; runtime vars are read after the bundle is frozen and do nothing. A `wrangler
deploy` from a laptop **overwrites** dashboard configuration, so prefer letting CI deploy.

### Two traps this walked into

**`pnpm deploy` silently does nothing.** It is a reserved pnpm workspace command that shadows the
script, and fails with `ERR_PNPM_NOTHING_TO_DEPLOY` rather than deploying. Use `pnpm run deploy`.

**A build's `status` field reads `stopped` whether it succeeded or failed.** Only the logs
distinguish them. Do not infer success from status alone.

### Verify after any deploy

A build that succeeds but omits `NEXT_PUBLIC_ELEVENLABS_AGENT_ID` produces a site that looks
completely normal and silently falls back to simulated mode — no error, no warning. Check for the
"Simulated preview" badge, or grep the deployed bundle for the agent id.

## Known limitations accepted for v1.0.0

- **Cancel is a hard delete** keyed on `row_number` from a prior read. A concurrent write between
  the read and the delete would remove the wrong row. Acceptable for a single-caller demo;
  it would not be for real bookings.
- **Booking references are random with a collision retry** against rows read at request time.
  Two simultaneous bookings could in principle collide. Same reasoning.
- **Business rules are duplicated.** Service durations and branch→stylist tables are hardcoded in
  four n8n Code nodes and also live in `content/`. A drift test guards this; see the test in
  `artifacts/` coverage. Generating the workflow from `content/` was considered and deferred —
  it would compete with the live instance as the source of truth.
