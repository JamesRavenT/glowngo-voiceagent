# v0.1.3 — Cloudflare deployment

Retarget the build from Vercel to Cloudflare Workers via `@opennextjs/cloudflare`.
Rationale and rejected alternatives: [ADR-0005](../decisions/0005-cloudflare-workers-via-opennext.md).

> **Outcome (2026-07-17).** Chunks 1–3 shipped. Two things the plan did not anticipate, both now in
> ADR-0005: the adapter build needs `node-linker=hoisted` to run on Windows at all, and eslint needed
> its own `.open-next/**` ignore on top of `.gitignore`.
>
> **Chunk 2's verification could not be completed as written.** The `IMAGES` binding is confirmed
> working on workerd (1.9MB PNG → 59KB WebP), but `opennextjs-cloudflare preview` returns 500 for
> every route that reaches the Next server, so "all three images render in the page" was never
> observed. Cause unproven. Local development, the build, and both test suites are unaffected.

**Scope discipline:** no application code changes. Nothing under `components/`, `content/`, or
`lib/` changes behaviour. `app/` is untouched. This is a build-and-deploy change only.

## Chunk 1 — Adapter and Worker config

**Goal:** `opennextjs-cloudflare build` produces a working Worker.

1. `pnpm add @opennextjs/cloudflare` and `pnpm add -D wrangler`.
2. Create `wrangler.jsonc`:

```jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "main": ".open-next/worker.js",
  "name": "glowngo-voiceagent",
  "compatibility_date": "2025-03-25",
  "compatibility_flags": ["nodejs_compat", "global_fetch_strictly_public"],
  "assets": { "directory": ".open-next/assets", "binding": "ASSETS" }
}
```

3. Create `open-next.config.ts`:

```ts
import { defineCloudflareConfig } from "@opennextjs/cloudflare";

export default defineCloudflareConfig();
```

4. Add scripts: `"preview": "opennextjs-cloudflare build && opennextjs-cloudflare preview"`,
   `"deploy": "opennextjs-cloudflare build && opennextjs-cloudflare deploy"`,
   `"cf-typegen": "wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts"`.
   **Leave `build`, `dev`, `start`, and `test:e2e` alone.**
5. Add `.open-next/`, `.wrangler/`, and `cloudflare-env.d.ts` to `.gitignore`.

**Notes for Codex**

- `nodejs_compat` and a `compatibility_date` of 2024-12-30 or later are both required — the adapter
  will not run without them.
- No R2 / Durable Object / queue bindings. Those exist for ISR and on-demand revalidation; this app
  has neither. Do not add them speculatively.
- If `keep_names` causes a runtime error from a library that stringifies functions, `"keep_names":
  false` is the documented escape hatch — but only add it if you actually hit the error.

**Done when:** `pnpm build` still passes unchanged, `pnpm typecheck` and `pnpm lint` pass, and
`opennextjs-cloudflare build` completes and produces `.open-next/worker.js`.

## Chunk 2 — Image optimization

**Goal:** the hero, navbar, and locations images render correctly on the Workers runtime.

Workers has no `sharp`, so Next's default image optimizer cannot run.

**Decided (James, 2026-07-17): use the Cloudflare `IMAGES` binding.** Add
`"images": { "binding": "IMAGES" }` to `wrangler.jsonc`. Real optimization, free-tier
transformation allowance far above portfolio traffic, and `next/image` call sites stay untouched.
The hero is the first impression — it gets a properly optimized LCP image.

`images: { unoptimized: true }` in `next.config.ts` is the **fallback only if the binding fails in
preview**. Do not reach for it first. If you do fall back, say so explicitly — it is a visible
quality regression on the hero, not a neutral swap.

**Done when:** all three images render at correct dimensions under `opennextjs-cloudflare preview`
(the real workerd runtime — `next dev` will not catch this class of bug), with no console errors.

## The one thing most likely to go wrong

**`NEXT_PUBLIC_*` are inlined at build time.** On Cloudflare they belong in **Workers Builds →
build variables**, never in Wrangler `vars`, which are runtime-only.

Set as a Wrangler var, `NEXT_PUBLIC_ELEVENLABS_AGENT_ID` is simply absent at build. `lib/env.ts`
then resolves to `simulated` — by design, since live requires mode *and* a non-empty ID. The result
is a site stuck behind the simulated badge, with **no error in any log**, and a config file that
looks correct. Anyone debugging this will lose an hour. It is called out in ADR-0005 and must be
called out in the runbook.
